作成: 2026-09-16 / 更新: 2026-09-19 /
状態: **§7 の 1〜5 まで実装済み（1〜3は実機確認OK・2026-09-17）。D1も作成済み。
判定が合わなかった記録は `flagged` で板に載ったまま、外すのは人（§10-6）。
残りは「既定を `api` にする」判断と、プライバシーの文言**

決めたこと: **無料枠のまま**・**検証はGitHub ActionsのバッチでNodeで再生**・
**同打数は `T3` 同順位**・**ギブアップを含むラウンドも登録可**（詳細は §8）。

固定ツアー（と週替わりチャレンジ）の合計打数を、全ユーザーで競えるようにする提案。
仕様の正本は `docs/spec.md` §6、残工程は `RELEASE_PLAN.md`「自己ベスト・ランキング」。

**先に決まっていないと作れないもの**（この設計の前提）:

- **固定9ホールのシード列が確定していること。** 板（ランキングの単位）はシード列から作る。
  並びが変われば別の板になり、記録は引き継げない（`seedsId` と同じ考え方）
- v2をツアーへ繋ぐか（`PROJECT_STATUS.md` 7-1）。板IDに生成器の版を入れる
- 週替わりチャレンジの画面接続（同 11）。週替わりの板はその後で足す

いま作れるものは、**固定コースに依存しない部分**（Worker・D1・identity・API・保留再送・
純粋化のリファクタ）だけ。板の中身はコース確定後に差し込む。

参照実装は Multicolor Sweeper（`src/server/worker.ts`・`migrations/0001_ranking.sql`・
`src/ranking-shared.ts`・`src/ranking-client.ts`）。**構造はそのまま踏襲する**。
違うのは「何を競うか」と「検証のやり方」の2点だけ。

## 1. Puttとスイーパーで違うところ

| | Multicolor Sweeper | Putt |
|---|---|---|
| 競う値 | クリア時間 [ms] | 合計打数 |
| 同点 | ほぼ起きない | **大量に起きる**（9ホールで38打は何十人も並ぶ） |
| 板の数 | 地雷数3種で固定 | コース差し替えと週替わりで**増え続ける** |
| リプレイの大きさ | 操作列（最大1000件） | **1打 = 数値2つ**。9ホール40打でも1KB未満 |
| 検証コスト | 盤面再生成＋操作再生（軽い） | **コース生成が重い**（後述 §4） |

つまり **「同点の扱い」と「板の増え方」はPutt側で新しく決める**必要がある。
一方で**リプレイのデータは極端に小さい**ので、送ること自体は何の問題もない。

## 2. 何を競うか（板の単位）

### 2-1. 板ID

ランキングは**板（board）ごと**に持つ。板IDは文字列1本で表し、これが違えば別のランキング。

```
tour:<tourId>:<generator>:<fingerprint>:r<rulesVersion>   例) tour:expert:v2:91cc132:r1
weekly:<challenge.id>:r<rulesVersion>                     例) weekly:weekly-v1-2026-09-14:r1
```

- `fingerprint` は**コースの作り方そのもののFNV-1a**（`tourFingerprint`）。
  シード列・生成器・コースの仕立て（`setup`）・ホールごとの上書き（`holes`）を全部入れる。
  **シード列だけでは足りない**（2026-09-19）。いまの固定コースは
  「シードは同じまま細い道を1本足す」で中身が変わるので、シードだけだと板が分かれない
- 名前と説明は指紋に入れない（変えても同じコースなので、板を分ける理由がない）
- `generator` は `TourDefinition.generator`。指紋にも入っているが、
  **板IDを見ただけで世代が分かる**ように表にも出す
- `rulesVersion` は**手で上げる定数**。`CONFIG.physics`・罰打・カップ判定・コース生成の
  数値を変えたら、過去の記録と比べられなくなるので上げる。上げ忘れを機械では検出できないので、
  `src/config.ts` の物理まわりにコメントで明示する（**触ったら上げる**）
- **古い板は消さない。** 表示はしないが記録は残す（後から「あの頃の板」を出せる）

### 2-2. 板の寿命

- 通常ツアー: コースを差し替えるまで。差し替え時は新しい板が空から始まる
- 週替わり: その週のみ。過去週は読み取り専用で残す

### 2-3. 練習モード

**ランキング対象外**（`docs/spec.md` §6）。送信もしない。

## 3. 順位の決め方

### 3-1. 主キーは合計打数、同点は「先に出した人が上」（**決定・2026-09-16**）

```
ORDER BY total_strokes ASC, achieved_at ASC, player_id ASC
```

- 表示は**ゴルフ流の同順位表記**にする（`T3` / `3T` ではなく `T3`）。
  38打が12人なら12人とも `T3` で、次は `T15`。内部順序は上の式で一意に決まるが、
  **画面では同打数を並べ替えない**（0.1打の差が無い競技で恣意的な上下を見せない）
- 「先に出した人が上」は、自己ベストの既存ルール（**同打数は更新扱いにしない**）と整合する。
  一度38打を出した人は、何度38打を出しても順位が動かない

### 3-2. 採らなかった同点の切り方

- **合計転がり距離 / 合計時間**: 競技の軸が「打数」から「速さ」へずれる。
  ゆっくり読む人が不利になり、`docs/spec.md` の「リアルなのは体験」と噛み合わない
- **カップまでの残り距離の合計**: 全ホールカップインするので常に0
- **ホール別の勝ち数（マッチプレー式）**: 板全体の一列の並びを作れない

### 3-3. ギブアップを含むラウンド（**決定・2026-09-16: 登録可**）

- ギブアップは**ダブルパー以降にしか出せず、その時点の実打数のまま記録される**（丸めない）。
  打数が減ることはないので、**登録を許しても不公平にはならない**
- ただしスコアカードと同じく `*` を残し、ランキングでも打数の後ろに `*` を出す
- **代案**: 全ホールカップインしたラウンドだけ登録する。分かりやすいが、
  「1ホールだけ崩れた人が登録すらできない」ので**採らなかった**

### 3-4. 登録のきっかけ

**自己ベストを更新したときだけ送る**（スイーパーの `canSubmitResult(newBest)` と同じ）。
同打数は更新扱いにしないので送信もしない。サーバ側でも `excluded < records` で上書きを守る。

## 4. 不正対策（**最大の判断どころ**）

### 4-0. 何の話か

ランキングのAPIは**誰でも直接叩ける**。ブラウザの開発者ツールを開ける人なら、
1打も打たずに「合計30打」をPOSTできる。順位が1人の嘘で埋まると、
**残りの全員にとって板が意味を失う**。何かは要る。

「リプレイ検証」は、スコアと一緒に**その打ち出しの列**（1打ごとの初速と方向）を送らせ、
**サーバ側で同じ物理を最初から回し直して、本当にその打数で上がれるかを確かめる**やり方。
合わなければ弾く。スイーパーで操作列を再生しているのと同じ考え方で、
Puttは1打が数値2つで済むぶん、送るデータはむしろ小さい（§4-1）。

やらない場合に残るのは、形の検証・打数の下限・レート制限だけ（段1）。
**嘘のスコアそのものは通る**ので、「身内で遊ぶ間は困らないが、晒されたら終わる」水準になる。

### 4-1. Puttはリプレイ検証に向いている

- 物理は**固定タイムステップ 1/240 秒で決定論的**（`src/physics.ts` 冒頭の約束どおり）
- 罰打の戻し先は `shotStart`（打つ前の位置）で固定。乱数も時刻も入らない
- コースはシードだけで決まる
- **1打の入力は `(初速 m/s, 方向 rad)` の2つだけ。** 打った位置は前の打の結果なので送らなくてよい

→ **サーバはシードと打ち出しの列だけで、ラウンド全体を1mmの誤差なく再生できる。**
9ホール40打でも送信データは1KB未満（スイーパーの操作列より小さい）。

### 4-2. コストの実測（2026-09-16・Node 22・このコンテナ）

`generateCourse` → `Green` 構築 → `Roller` 再生を、風の丘の9シードで計測した。

| | コース生成 | ハイトマップ | 合計 |
|---|---|---|---|
| v1 | 5.1 ms/ホール | 10.0 ms/ホール | **15 ms/ホール** |
| v2 | 62.3 ms/ホール | 17.8 ms/ホール | **80 ms/ホール** |

転がりの再生は **0.46 ms/打**（9ホール72打で33ms）。つまり**重いのはコース生成側**で、
9ホール1ラウンドの検証は **v1で約140ms・v2で約720ms のCPU**。

### 4-3. Workers のCPU制限（**無料枠のまま行く・2026-09-16決定**）

- **無料プラン: 1リクエストあたり10ms CPU。** Puttは1ホールぶん（v1で15ms）すら入らない
- 有料（Workers Paid）は既定30秒だが、**当面は課金しない**
- ランキング**本体**（登録・取得・名前・削除）は無料枠で足りる。
  詰まるのは**検証だけ**（実装前に最新の制限値は確認する）

固定ツアーは全27ホールしかないので、生成済みの `Green` を isolate のモジュールスコープへ
キャッシュすれば2回目以降は0msになる。ただし**冷えた1回目が10msを超えて落ちる**ので、
無料枠では解決にならない。

#### なぜスイーパーは無料枠で検証できているのか

同じ環境で測ると、スイーパーのサーバ側検証は **0.35 ms/盤面 + 4.5 µs/操作**
（52手なら約0.6ms、上限1000手でも約5ms）。Puttの140〜720msとは**400〜2000倍**違う。理由は3つ。

1. **世界の大きさ。** 盤面は9×9の81マス。Puttのハイトマップは1ホール6.8〜8.6万セルで、
   9ホールぶんでは60〜78万セル
2. **重い探索をサーバがやっていない。** no-guess盤面の探索はクライアントが回し、
   サーバは**当たった `attempt` 番号を受け取って1回だけ生成し直す**。
   Puttには同じ近道が無い。物理を回すにはハイトマップが要る
3. 1手の再生が周囲8マスを見るだけ（4.5µs）なのに対し、Puttは1打で1/240秒を数百〜千ステップ、
   毎ステップ勾配を補間する（0.46ms）。ただし効くのは1と2のほう

**つまりスイーパーの作りをそのまま持ってきても、検証だけは同じようにはいかない。**

### 4-4. 段階で分ける（提案）

- **段1（必ず入れる・ほぼ0コスト）**
  - 形の検証（打数が整数・ホール数・parの一致・板IDが実在する・打ち出しの値域）
  - 常識チェック（1ホールの打数下限、合計打数の下限、1打の初速の上限＝スワイプの上限）
  - identity ごと・IPハッシュごとのレート制限（スイーパーの `rate_limits` をそのまま）
  - 同じ `submissionId` の二重登録を弾く（`submission_log` をそのまま）
- **段2（推奨・後から足せる）: リプレイ検証を非同期で**
  - 登録は即時受理し `verification_status = 'pending'` で板に載せる
  - 後から再生して `verified` / `flagged` を付ける
  - **`flagged` でも板からは外さない。** 機械の判定はこちらへの知らせで止め、
    板から外す（`suspicious`）かどうかは**人が決める**
  - 外した本人には「確認中」とだけ見せる
  - 走らせるのは GitHub Actions の定期バッチ（§4-4-1・案A）
- **段3（やらない）: 人間らしさの判定。** スワイプの生データを送って分布を見る、など。
  当たり判定より先に運用が破綻する

#### 4-4-1. 段2の実行場所（**決定・2026-09-16: 案A**）

- **案A: GitHub Actions のバッチ（採用）**
  - 定期実行のワークフローが D1 から `pending` の記録を読み、**Node上でゲーム本体のコードを
    そのまま使って再生**し、判定を書き戻す（`wrangler d1 execute --remote`）。
    `CLOUDFLARE_API_TOKEN` は既に `deploy-cloudflare.yml` で使っている
  - 720msはNodeでは何でもない。**CPUの制約が丸ごと消える**
  - three.js を避ける必要も無くなるので、**§4-6の `Green` 切り出しは不要になる**
    （`scripts/check-stuck.ts` が既に `Green` と `Roller` をNodeで動かしている）
  - 判定が付くまで数分〜数時間遅れる。**背景の整合性チェックなので困らない**
  - 弱点: 定期ワークフローはリポジトリが無活動だと止められる。公開リポジトリである必要もある
- **案B: ハイトマップを先に焼いてR2/KVへ置く**
  - 27ホールぶんの高さ・勾配を**ビルド時に計算**して置き、Workerは取ってきて物理だけ回す
  - Float32Array はそのまま読めるので、**1リクエストで1ホールぶんなら10msに入る見込み**
  - 置く量は1ホール約0.8MB（高さ・勾配2枚）で27ホール22MB前後
  - コースを差し替えるたびに焼き直しが要る。**仕組みが1つ増える**

**案Aを採る（2026-09-16）。** 検証は遅れてよい仕事で、Puttはコードが既にNodeで動く。
案Bは、Actionsの定期実行が使えなくなったときの退避先として残す。

### 4-5. 検証で分かることの限界（正直に書いておく）

リプレイ検証が示せるのは「**その打ち出しの列で、本当にその打数で上がれる**」ことだけ。
最適な狙いと初速を計算して投げるボットは、**物理的に正しいので弾けない**。
スイーパーの操作列検証も同じ性質で、目的は「ありえないスコアを弾く」ことに限る。
ここを越えようとしない。

### 4-6. そのために必要なリファクタ（**挙動は1mmも変えない**）

案Aでは検証がNodeで動くので、**three.js を避ける必要はない**
（`scripts/check-stuck.ts` が既に `Green` と `Roller` をNodeで動かしている）。
必要なのは1つだけになった。

1. **ホールの規則を純粋な関数へ切り出す（必須）。**
   いま `src/main.ts` にある「池・OBなら+1打して `shotStart` へ戻す」「`holed` でホールアウト」は
   画面から切り離して `src/hole-sim.ts`（仮）に置き、**ゲーム本体もそれを使う**。
   検証側に規則を書き写すと、直した片方だけが取り残される
2. **`Green` の three 非依存化（任意・やらない）。**
   `src/green.ts` の1〜394行（`Green` と `defaultGreenParams`）は `THREE.` を1度も使っておらず、
   `src/green-field.ts` へ機械的に移せることは確認済み。
   **案Bへ退避するときに必要になる**ので、ここに記録だけ残す
3. 確認方法は生成器v2のときと同じ。シード1〜200でサーフェスのダイジェストと
   ハイトマップの最小・最大高を突き合わせ、**コースが1mmも変わっていないこと**を示す

1は**ランキングの判断が付く前でも単独で入れられる**（`npm run check:stuck` 側も楽になる）。

## 5. サーバ（Cloudflare Workers + D1）

Putt の `wrangler.jsonc` は現在 Static Assets だけで `main` を持たない。
スイーパーと同じ形で Worker と D1 を足す。

```jsonc
"main": "./src/server/worker.ts",
"assets": { "directory": "./dist", "not_found_handling": "none", "run_worker_first": ["/api/*"] },
"d1_databases": [{ "binding": "DB", "database_name": "putt-ranking", "migrations_dir": "migrations" }]
```

- **D1はスイーパーと分ける**（別ゲーム・別スキーマ・別の消し方。同居の利点がない）
- **GitHub Pages（退避先）ではAPIが無い。** `/putt/` で遊んでいる間はランキングを
  「利用できません」と出すだけで、ゲームは普通に遊べること（`DEPLOY.md` のベースパスで判別する）

### 5-1. テーブル（スイーパーの4表をほぼそのまま）

- `players(player_id, credential_hash, display_name, created_at, updated_at)`
- `records(player_id, board_id, total_strokes, total_par, hole_strokes_json, gave_up,
  generator, rules_version, app_version, shots_json, verification_status, achieved_at, updated_at)`
  - 主キーは `(player_id, board_id)`。**1人1板1件**（ベストだけ持つ）
  - 索引は `(board_id, verification_status, total_strokes, achieved_at, player_id)`
  - `shots_json` はリプレイ用（`[[speed, dir], ...]` をホール別に）。段2を後から有効にできるよう、
    **段1しか実装していない時点でも受け取って保存する**
- `submission_log(submission_id, player_id, board_id, status, response_json, created_at)`
- `rate_limits(rate_key, window_start, count)`

### 5-2. API（スイーパーと同じ形）

| メソッド | パス | 内容 |
|---|---|---|
| GET | `/api/health` | 死活 |
| GET | `/api/rankings?board=<boardId>&limit=50` | 上位＋自分の周辺±3＋`yourRank` / `yourBest` |
| POST | `/api/records` | 登録（`submissionId` で冪等） |
| PUT | `/api/player` | 表示名の更新 |
| DELETE | `/api/player` | **自分の記録と名前を全部消す** |

- 認証は `Authorization: Bearer <playerId>.<credential>`。サーバはcredentialのSHA-256だけ持つ
- 表示名は16文字まで・NFC正規化・制御文字と `<>` を弾く（`normalizeDisplayName` をそのまま）

### 5-3. 個人情報

- 持つのは**匿名ID・認証用ハッシュ・表示名・スコア・リプレイ**だけ。IPは保存せず、
  レート制限のキーにハッシュとして使うだけ（スイーパーと同じ）
- **`DELETE /api/player` を最初から実装する。** 消し方が無い状態で公開しない
- `docs/spec.md` §6 の約束どおり、**扱う情報と削除方法が確定したら
  ハブ（`https://hanage.app/privacy/`）のポリシーを同じ変更で更新する**

## 6. クライアント側

### 6-1. identity と名前

- `putt-player-identity-v1` に `{ playerId, credential }`（`crypto.randomUUID` + 32バイト乱数）
- **localStorageに閉じるので端末を変えると引き継げない。** これは仕様として受け入れる
  （引き継ぎコードは初回公開の条件に無い。やるなら後から）
- 名前は**初めて登録するとき**にラウンド終了カードの上で聞く。空なら `PLAYER`。
  後から変えられる場所はトップメニュー（パター選択の並び）に置く

### 6-2. 送信

- 入口は既存の `onRoundComplete`（`src/entry.ts`）。`TourBestScoreStore.record()` が
  `isNewBest` のときだけ送る
- **失敗してもゲームを止めない**（`RELEASE_PLAN.md` の完了条件）。
  オフライン対応済み（PWA）なので、**送れなかったものは `putt-pending-submission` に積んで
  次回起動時に再送**する。積むのは板ごとに最新の1件だけでよい
- 送る中身: `submissionId` / `boardId` / 表示名 / ホール別打数と `holedOut` / 合計 /
  打ち出しの列 / `generator` / `rulesVersion` / `appVersion` / `putterPowerScale`
  - `putterPowerScale`（スワイプ→初速の個人調整、0.5〜1.5）は**再現には要らない**が、
    分布を見たいので送る。**性能差ではなく感度なので、値そのものは順位に使わない**
  - パターの形状は**見た目だけで性能差を付けない約束**（`docs/spec.md` §5）なので送らない

### 6-3. 動線（**コースの確定を待たずに作れる**）

板IDは文字列1本なので、**どのシードが入るかは画面に一切影響しない**。
動線・UI・文言・失敗時の見え方は、モックのランキングAPIを相手に先に作って**実機確認まで通せる**。
むしろ実機確認が要るのはここなので、先に作る価値がある。

#### 登録（ラウンド終了）

```
9ホール目ホールアウト → ROUND_END カード
  ├ 自己ベスト更新でない → 今までどおり（BEST の行だけ）。送信しない
  └ 自己ベスト更新 → NEW BEST!
       ├ 名前が未設定 → カードの上に名前入力を1枚（16字・空なら PLAYER・「あとで」で閉じられる）
       └ 名前あり → **確認を挟まず自動で送る**
            ├ 成功 → `T12 / 340人` を BEST の下に出す。「ランキング」ボタンが有効になる
            ├ 失敗・オフライン → `あとで登録します` とだけ出す（保留に積む）。**ゲームは止めない**
            └ 確認中（段2で pending のとき）→ `確認中` と出す
```

- **「登録しますか？」とは聞かない。** 遊ぶ側の一手間を増やさない（`CLAUDE.md` の原則）。
  名前を聞くのは初回だけ
- 「あとで」で名前を入れなかった場合は送らない。次に更新したときにまた聞く
- ボタンの並びは今の `コース選択へ / もう一度 / トップへ` に**「ランキング」を足して4つ**。
  9ホールの一覧が出るカードは既に高さがぎりぎり（`#score-card.list` で中身だけスクロール）なので、
  **実機で 320×568 に収まるかを必ず見る**。収まらなければ「ランキング」は一覧の上へ1行で置く

#### 閲覧（トップから）

```
トップメニュー
  ├ 通常ツアー → コース選択
  ├ 練習（対象外）
  ├ パターを選ぶ
  └ ランキング ← 足す（色を落とした sub ボタン。パターと同じ扱い）
        → ランキング（**1枚で完結**）
             [風の丘][曲がりの森][水鏡の庭]  ← タブで板を切り替える
             あなた: 名前 / 順位 / 打数        ← 表の中から自分を探させない
             表
             記録を全部消す                    ← 一番下に文字だけで
```

- **板ごとに画面を分けない。** 一覧を1枚挟むと、トップから表まで3回押すことになる。
  スイーパーと同じでタブにして、**押す回数を2回に減らす**（2026-09-17・実機の指摘）
- タブは視点バーと同じ12pxで3つを1行に収める。英語のコース名は枠の中で折り返す
- **言語の切り替えはここに置かない**（パター選択と同じ。トップにだけ置く）
- **コースの説明も出さない。** 選ぶための情報はコース選択が持っていればよく、
  ランキングで要るのは名前だけ
- ラウンド終了カードからも同じ画面へ入る（そのコースのタブが開いた状態）

#### あなたの行（表の上）

- `あなた <名前> [名前を変える]` と `順位 T64 / 341人` `打数 47 (+11)`
- **自分の順位を表の中から探させない。** 圏外でも、まだ登録していなくても、
  同じ場所に同じ形で出る（記録が無ければ `--`、検証待ちなら `確認中`）
- 名前を決める入口もここ。**トップのボタンをこれ以上増やさない**

#### ランキング表

- 1行 = `順位 / 名前 / 打数`。パー差は打数の隣に小さく、ギブアップを含む記録は `*`
- **自分の行はコースの色で反転**させる（今の `course-best` と同じ扱い）
- 上位10件＋**自分の周辺±3**。間が飛ぶところは `…` の行を1本入れる
- 同打数は**同じ順位番号**（`T3`）。並べ替えない
- 枠は画面に収め、**中身だけ縦スクロール**（`#score-card.list` と同じやり方）
- 自分の記録が無い板では、表の下に `まだ登録がありません` とだけ出す

### 6-4. 失敗したときの見え方（**ゲームを止めない**）

| 場面 | 見せ方 |
|---|---|
| 送信に失敗・オフライン | `あとで登録します`。保留に積んで次回起動時に再送 |
| 取得に失敗 | 表の代わりに `いま見られません`＋`もう一度` |
| GitHub Pages（`/putt/`）で開いている | ランキングの入口を**出さない**（APIが無い） |
| 名前が未設定 | 送らない。順位の行も出さない |
| 人が `suspicious` にした | 本人にだけ `確認中`。板には出さない |
| 段2が `flagged` にした | **何も変わらない**（板に載ったまま・順位も出る） |

### 6-5. 文言と数値の置き場所

- 文言は二言語（`src/i18n.ts`）。英語はゴルフの言い方に揃える（`T12` / `NO ENTRIES YET` など）
- 件数・保存キー・再送の間隔などは `CONFIG.game.ranking` へ置く
  （**マジックナンバーを他のファイルに書かない**という約束のとおり）
- 文言を足したら `npm run font:pixel` でサブセットを作り直す（ドット絵フォント）

### 6-6. モックで先に作る

`src/ranking-client.ts` の関数（`fetchRanking` / `submitRecord` / `updatePlayerName`）を
**インターフェースとして先に決め**、中身を localStorage の偽データに差し替えたモックを置く。

- Worker も D1 も無い状態で、**動線・UI・失敗時の見え方・実機確認まで全部できる**
- 成功・失敗・オフライン・名前未設定・圏外・同打数だらけの板を、モック側で意図的に作れる
  （**実機で確認したいのはこの分岐**で、本物のサーバでは再現しにくい）
- 本物ができたら `fetch` に差し替えるだけ。`?ranking=mock` でモックに戻せるようにしておくと、
  後からUIだけ直すときに楽

### 10-4. 登録と取得（段4・2026-09-19）

- **`POST /api/records`**: 自己ベストのときだけ書き換える（`WHERE excluded.total_strokes <
  records.total_strokes`）。同じ `submissionId` は `submission_log` で弾き、
  **1回目と同じ答えを返す**（電波が切れて送り直しても二重登録にならない）
- **`GET /api/rankings`**: 上位10件＋自分の周辺±3。
  **同打数は `RANK()`（打数だけで並べる）で同じ番号**になり、次が飛ぶ。
  切り出しは `ROW_NUMBER()`（打数 → 到達時刻 → playerId）で行う。
  **板から外れるのは `suspicious` だけ**（`pending`・`flagged` は載せる）
- **段1の検証**（`src/server/record-validation.ts`）: ホールの形・par・打数の範囲、
  **合計を数え直して突き合わせ**、規則の版、ありえない初速、打数より多い打ち出し。
  `shots` は空でもよい（途中保存から再開したラウンドでは揃わない）
- **打ち出しの列を積み始めた。** `launch()` が `[初速, 方向]` をホールごとに溜め、
  ホールアウトで `Round` に入り、ラウンド完走でそのまま送られる。
  進行の保存にも入るが**後から足した任意項目**なので、古い保存の復元は壊れない
- 登録直後の状態は `CONFIG.game.ranking.server.initialStatus`。
  **段5（リプレイ検証）を入れたら `pending` にする**

### 10-5. リプレイ検証（段5・2026-09-19）

**Workerの外で回す**（案A）。GitHub Actions が6時間ごとに `scripts/verify-records.ts` を
走らせ、`pending` の記録を再生して `verified` / `flagged` を書き戻す。

#### ホールの組み立てを1本化した（`src/course/hole-build.ts`）

再生でいちばん怖いのは**コースの作り方が1mmずれること**。ずれれば「本人の画面では42打・
サーバでは43打」になり、しかもそれが他人の順位を動かす。

組み立ては `main.ts` と `scripts/check-stuck.ts` に**同じものが2つ**あった
（検証を足せば3つ目になる）ので、`hole-build.ts` へ出して3か所とも同じ関数を通した。

- `tourHoleCourse(tour, seed)` … 生成器はツアーが持つが、**ホール単位で上書きできる**
- `buildHoleGreen(course, setup)` … うねりの振幅は **`LIVE_UNDULATION_AMPLITUDE`**。
  本番は `main.ts` の既定モードで `compareEnhancedAmplitude`（0.20）を使っており、
  **`defaultGreenParams()` の 0.15 ではない**。ここを取り違えると転がりが変わる
- `buildHoleRoller(green, course, setup)` … グリーンの速さは仕立てが決める

**切り出しの前後で4コース36ホールのダイジェスト（高さ41×41点＋サーフェス）が完全一致**する
ことを確かめてある。`npm run check:stuck -- --tour=beginner` も通る。

#### 判定

| 結果 | いつ | どうなる |
|---|---|---|
| `verified` | 再生した打数・カップインが全ホール一致 | そのまま板に載る |
| `flagged` | 1ホールでも合わない | **板には載ったまま。** 人の判断待ち |
| 保留（`pending` のまま） | 打ち出しの列が無い・止まらない・古い板・規則の版違い | 板には載ったまま |
| `suspicious` | **人が黒と決めたときだけ**（手で書く） | 板から外れる。本人にだけ `確認中` |

**分からないものを `flagged` にしない。** 疑わしきは罰せず、判定できないものは保留にする。
**そして `flagged` も板から外す判定ではない。**

#### `pending` は板に載る

登録の直後は `pending`（`CONFIG...server.initialStatus`）。判定は数時間遅れるので、
**その間も順位は出す**。ラウンド終了カードも「確認中」ではなく順位を出す
（`確認中` と出すのは、板から外れて順位が無くなったときだけ）。

#### 手元のD1で通したこと

| 試したこと | 結果 |
|---|---|
| 正しい記録を `POST /api/records` | `status: pending` で受理、順位1位 |
| それを検証 | **`verified`（9ホール458ms）** |
| 打数を1ずつ減らして申告 | **段1で弾かれた**（`too many shots`。打った数より打数が少ない） |
| 打数はそのままで「全ホールカップインした」と嘘 | 段1は通って `pending`・1位（同点）→ **検証が57msで見抜いた**（§10-6 以降はここが `flagged`） |
| そのあとの板 | 嘘の記録は**消えて**、本人からは `yourRank: null` ＋ 自分の記録あり（＝`確認中`） |
| もう一度検証 | `検証待ち: 0件`（二度判定しない） |

### 10-6. `flagged`（判断は人・2026-09-19）

機械の判定だけで記録を板から外さないことにした。**物理の版ずれ・端末差・取りこぼしで
ちゃんと遊んだ人の記録が黙って消えるほうが、嘘が1件混じるより悪い**（§1の前提）。

```
登録 → pending（板に載る・順位も出る）
   ↓ 6時間ごとのバッチが再生
  合う  → verified（そのまま）
  合わない → flagged（★板には載ったまま。順位も出る）
                 ↓ 持ち主が判断
              問題なし → verified
              クロ    → suspicious（ここで初めて板から外れる）
```

- 状態を4つに増やしたので **D1の移行を1本足した**（`migrations/0002_flagged_status.sql`）。
  SQLite は CHECK だけを後から変えられないので**表を作り直して移す**。
  本番の記録がゼロのうちにやってある
- 板に載せる状態は `BOARD_VISIBLE_STATUSES`（`src/ranking-shared.ts`）が正本。
  Worker の並びの問い合わせはこれを展開するだけ
- **通知は検証ワークフローをわざと失敗させて出す。** `flagged` が1件でも出ると
  バッチの終了コードが1になり、定期実行が赤くなって GitHub が持ち主へメールを送る。
  板・プレイヤー・理由は実行結果の Summary に表で出る
- **判断が済むまで毎回赤いまま。** バッチはその回で付けたものだけでなく、
  残っている `flagged` を全部数えて失敗する（メールを1通見落としても次でまた気づける）
- 書き換えのコマンドは `DEPLOY.md`。`pending` に戻せば次のバッチが再生し直す
- 移行の適用は Actions の **`Apply D1 migrations`**（手で押す。`dry: true` で一覧だけ）。
  デプロイには混ぜない。**表の作り直しを含む移行を、気づかないうちに流さない**

#### 規則を変えるとき

**罰打・物理・カップ判定・コース生成の数値を変えたら
`CONFIG.game.ranking.rulesVersion` を上げる。** 版は板IDに入るので、上げれば
古い記録は古い板に残り、新しい記録と混ざらない。

上げ忘れたときに起きるのは、**古い `pending` が新しい規則で再生されて打数が合わず
`flagged` が並ぶ**こと。`flagged` は板に載ったままなので**記録は消えない**が、
人が1件ずつ見る手間だけが増える。検証側でも `records.rules_version` が
いまの版と違うものは判定せずに保留する（二重の保険）。

罰打の規則そのものは `src/hole-sim.ts` の `penaltyStrokes()` 1か所。
ゲーム本体と検証が同じ関数を見ているので、**そこだけ直せば両方が揃う。**
