#### 2回目の実機確認で出た指摘と、その対応（2026-09-15）

**レイアウトはOK。** 残り2点を直した。

| 指摘 | 対応 | 実測（前 → 後） |
|---|---|---|
| バンカーが浅い。可能なら深く | `hollowGradient` 0.08 → 0.28、窪みを砂の内側へ収めた | すり鉢の深さ 中央6.6→**16.3cm** / 最大10.4→**26.1cm** |

**深さは出やすさをほとんど左右しない。** 砂から出るのに要る初速は
`sqrt(2 * (摩擦 * 距離 + 5/7 * g * 深さ))` で、半径1.5mのバンカーなら平らでも 3.63 m/s 要り、
25cm 窪ませても 3.95 m/s（+9%）。**効いているのは砂の摩擦であって深さではない。**

窪みは**砂の内側に収める**。輪郭の歪みは半径を角度ごとに (1 ± amplitude) 倍するので、
(1 - amplitude) 倍までに収めればどの向きでも砂の中に入る。
はみ出すとバンカー脇の芝が「止まれない斜面」になり、手前に刻めなくなる。

パー基準はこれ以上上げると par5 の候補が急に減る（[13,24,32] で 286本 → 130本）ので、
9ホールを組むことを考えるとここが上限に近い。ついでに par6 が消えた。

#### 3回目の実機確認で出た指摘と、その対応（2026-09-15）

| 指摘 | 対応 | 実測（前 → 後） |
|---|---|---|
| 円型の窪みができている。バンカー面全体が、境界を起点に窪んでほしい | 窪みの形を作り直した（下記） | 断面で砂の範囲と窪みの範囲が一致 |
| 深さは今ちょっと深め。現在の値を最大にしてばらつかせて | 深さをバンカーごとに引く | 一律26cm → **5.1〜25.6cm（中央14.2cm）** |
| パーを9ホールあたりあと3打厳しく。距離を伸ばせないか | **距離と par の境目を一緒に伸ばした** | 9ホールの合計距離 163m → **191m（+28m ≒ 3.1打）** |

**窪みの形。** 前は「輪郭とは無関係な楕円を内接させて `(1-r^2)^2` で窪ませる」作りだったので、
歪んだ輪郭の中に円い窪みが浮いていた。いまは**輪郭までの正規化距離 q**（角度ごとの歪みで
割った値。砂の縁でちょうど 1）を使い、高さを `1 - q^n` にしている。

- q = 1（砂の縁）でちょうど 0。**外の芝には一切斜面が出ない**
- 傾きは縁でいちばん急。底は平ら（＝縁を起点に落ちる皿）
- 輪郭がどれだけ崩れていても縁が高さ0なので、**ひょうたん型でも砂の面全体が窪む**

**距離とパー。** par の境目だけを動かしても境目付近のホールしか変わらない。
ツアーは PAR3×2・PAR4×5・PAR5×2 の PAR36 で固定なので、
**同じ par のホールが長くなること**が「パーに対して厳しい」に直結する。
だから距離と境目を一緒に伸ばした（PAR4の中央 18.1m → 21.3m、PAR5 の中央 25.6m → 30.5m）。

**par3 の境目だけはほとんど動かせない。** par3 は「1打で乗せて2パット」なので、届かない
距離にすると成立しない。最強の一打が平らな通常芝で 14.6m しか転がらないため 13m が上限。
厳しくするぶんは par4 と par5（9ホール中7本）で作っている。

## 5. OBまわり（境界の見え方と、入ったときの知らせ）

### 5-1. 境界の視認性

プレイ中、どこからOBなのかが直感的に分かりづらいことがある。
これは単なる見た目ではなく、プレイヤーが安全な打ち先を判断できるかに関わる。

候補:

- OB側に白杭などの境界マーカーを置く
- セカンドカットとOBの色・質感差を少し強くする
- コースマップでも境界が読み取りやすいか確認する

実装前に、通常画面・コースマップの両方で邪魔にならない最小の表現を選ぶ。

審査前の実機確認では改善要求が出なかったため、一度はP0-2として着手しないと判断した（`RELEASE_PLAN.md`）。
**5-2の知らせを入れた後も「分かりづらい」と残ったので、着手対象に戻す（2026-09-16）。**

#### 直すときの注意

- **コース生成器とは無関係。** 触るのは `src/green.ts` の頂点色と
  `CONFIG.green.surfaceColors.ob` だけで、生成器（v1・v2とも）は関係ない
- **境界の「形」を変えて解決しないこと。** 形を決めているのは `CONFIG.course.edgeNoise` で、
  ここは**v1とv2で共有している**。触ると既存3ツアー全27ホールの外形が変わり、
  自己ベストとラウンド進行も無効になる。**色・コントラスト・目印で解決する**

#### 分かったこと: 地面の色では直せない（2026-09-19・実測）

着手する前に、**「色を強くする」で解けるのかを先に測った。解けない。**

芝の頂点カラーは高さで明暗が振れる（`shade.heightStrength` 0.75。明るい＝高い）。
一方OBは高さを読ませないので単色（`flatSurfaces`）。**片方だけが振れる**ので、
境目の明暗差は場所によって符号ごと変わる。

本番36ホールの境界を 0.25m 刻みで走査し、隣り合う「打てる地面 / OB」の組 12536 個について
頂点カラーの輝度差を出した（255階調・OB側を基準）。

| | 値 |
|---|---:|
| **打てる側のほうが暗い（明暗が逆転）** | **5564 組 (44.4%)** |
| 明暗差が20未満（ほぼ見分けられない） | 3132 組 (25.0%) |
| 明暗差の分位（25% / 中央 / 75%） | **−22 / 15 / 89** |

分位が −22 と +89 に割れているのが答え。**「暗い＝OB」という手掛かりが、
コースの半分では逆を向く。** これは手掛かりが弱いのではなく、嘘をついている状態で、
`surfaceColors.ob` をどう選び直しても片側は必ず裏切る
（OBを一番暗い芝より暗くすれば揃うが、輝度20以下＝ほぼ黒になり、
枠の外の地面 `surround` より暗いという別の矛盾が出る）。

→ **高さの濃淡を受けない目印が要る。**

#### 「ゲーム側が引いている線」にした（2026-09-19・**確定**）

**最初は白杭（1m の白い円柱を3m間隔）で作ったが、実機前のプレビューで見て取りやめた。**
続けて、表示メッシュの頂点カラーをOB側だけ白で塗る「地面に引いた白線」も試したが、
**太すぎた**（マスが 0.156m なので、これ以上細くできない。砂利道のように見える）。

採ったのは**現実の白線を真似ない**やり方。

> コースに馴染ませなくていい。リアルにあるものではなく、
> **ゲームだから見えている線**という設定でくっきりでいい。ただしピクセル感は保つ

- **方向ガイドと同じ `THREE.Line`** で境界をなぞる（`createObBoundaryLine`）。
  WebGL の線は常に1デバイスピクセル幅なので、低解像度ターゲット上では**常に1ドット**。
  **距離で太さが変わらない**し、`LineBasicMaterial` はライトを受けないので、
  遠くでも陰の中でも同じ濃さで出る。太さ・粒の大きさは方向ガイドとちょうど同じ
- 形は `green.surfaceAt` からしか読まない。**生成器にも `edgeNoise` にも触れない**
- マーチングスクエアで線分の集まりとして取り出す。輪郭として順番に繋ぐ必要がないので
  `LineSegments` 1つ・ドローコール1つで済む
- 格子の目のままだと階段になるので、**辺の上で二分探索**して実際の境界位置まで寄せる
  （6回で 0.25m / 2^6 ≒ 4mm）
- 1ホール **229〜480本**（平均350）。生成は1ホール **15.8ms**
- **池際には引かない。** 池が境界に乗っているところでは線が途切れて、その先で再開する
  （白線はOBの印であって、ハザードの印ではない）

**地形には隠れる**（`depthTest` そのまま）。丘の向こう側は見えないが、稜線の上には出るので、
低い視点でも左右どちらが切れているかは読める。

**物理には一切関わらない。** 乱数も引かないので木の配置も1本もずれない。

#### 目立ちすぎたので落とした（2026-09-19・プレビュー確認）

素の白・不透明のままだと「思ったより目立つ」と出た。線そのものは残したいので、
**強さのほうを落とす**。

- **半透明にした**（`opacity` 0.55）
- **カメラから遠いほど薄くする**（4m まではそのまま → 18m で `farOpacity` 0.16）。
  境界は「今いるあたりでどこまで打てるか」を読むためのものなので、
  遠くまで同じ濃さで出ていると画面がうるさいだけになる
- そのために `LineBasicMaterial` をやめ、**ビュー空間の深度で不透明度を決める素のシェーダ**にした。
  `uFade` を 0 にするとフェードが止まる
- **コースマップだけは別扱い**（`setMapMode`）。図として読むところなので、
  距離で薄くせず、`depthTest` も切って全線を出す

**太くはできない。** WebGL の `THREE.Line` は線幅を指定できず必ず1デバイスピクセルで、
そこが「常に1ドット・距離で太さが変わらない」という利点の裏返しになっている。
太くするには画面幅で押し広げるリボンのメッシュに作り替えることになり、
ドット1個きざみでなくなるぶんピクセル感が崩れる。今は**濃さだけで調整している**。

#### 3つ作って見比べ、なめらかな線に決めた（2026-09-19・プレビュー確認）

太さの作り方を3つ用意して `?obline=` で見比べ、**`smooth` に決めた。残り2つは消した。**

| | 太さ | ピクセル感 | 地形・木に隠れる | 結果 |
|---|---|---|---|---|
| `dot` | 常に1ドット（変えられない） | そのまま | 隠れる | 細すぎ・太くできない |
| `ribbon` | 選べる | そのまま | 隠れる | — |
| **`smooth`** | **選べる** | 崩れる（なめらか） | **隠れない** | **採用** |

採ったのは**補助線の「滑らか」と同じ高解像度Canvas**（`SmoothLineOverlay`）へ相乗りする方式。
3Dのドット化とは別に画面の実解像度で描くので、**ドットの粒に縛られず太さを選べる**。

- **このCanvasは深度を持てないので、丘の裏も木の裏も透ける。**
  「地形どおりに隠れる」は `dot` / `ribbon` を捨てた時点で諦めた
- 濃さは8段に丸めて段ごとに1回だけ stroke する（1本ずつ描くと毎フレーム数百回になる）
- 距離で薄くするのは3D版と同じ式を CPU 側でやる。**マップだけは薄くしない**

**数字はプレビューで2回落とした。**

| | 最初 | → | → | 現在 |
|---|---:|---:|---:|---:|
| 太さ [CSS px] | — | — | 1.5 | **3** |
| 手前の不透明度 | 1.0 | 0.55 | 0.35 | **0.18** |
| 遠くの不透明度 | — | 0.16 | 0.10 | **0.05** |

#### 途切れていたのを直した（2026-09-19・プレビュー確認）

「途切れて見える」の中身は2つあった。**端点が繋がっていない点を数えて切り分けた。**

| | 直す前 | 直した後 |
|---|---:|---:|
| **枠ぎわ**（コース枠に達して線が開いていた） | **132点** | **0点** |
| 内側（池で線が切れている。意図どおり） | 12点 | 12点 |

- **枠ぎわは作りの穴だった。** 走査の格子がコース枠ちょうどで終わっていたので、
  芝が枠に届いているホールでは輪が閉じなかった。
  **格子を枠の外へ1マスぶん広げた**（枠の外は必ずOBなので、これで必ず閉じる）
- **マップの途中で切れて見えたのは木の傘**だった。木を0本にすると途切れが消えることで確認。
  マップでは `depthTest` を切ったので、今は木の下も繋がって見える
- 内側の12点は池の切れ目。池が境界に乗っているところで線が途切れ、その先で再開する

#### 分かっていること

- 浮かせ量 `lift` は 0.02m。0.06m まで上げても見え方は変わらなかったので、
  Zファイティングも地形へのめり込みも起きていない
- 1ホール 375〜404本（最大498）。生成は1ホール 16.2ms

#### 確定（2026-09-19）

プレビューで4回見比べ、**太さ3px / 手前 0.18 / 遠く 0.05 で確定**。

- 濃さは **1.0 →（目立つ）→ 0.55 →（まだ目立つ）→ 0.35 →（まだ目立つ）→ 0.18**
- 太さは 1.5px →（細い）→ **3px**
- 出し方は **`dot`（1ドット）/ `ribbon`（帯）/ `smooth`（なめらか）を作って見比べ、`smooth`**

**色は最後まで触っていない。** 上の実測どおり色だけでは解けないためで、
まだ足りないと出たときは「OBを一番暗い芝より暗くし、`surround` も合わせて下げる」を測り直す。

仕様は `docs/spec.md` §1「OB境界の線」へ反映した。

#### 実機で出た指摘と直し（2026-09-20・2回目）

> 全体に1.5倍濃くして
> 打った後のカメラでは境界表示しないで、邪魔なので
> （ただし打った直後最初のプレイヤー視点カメラではOBに入ったかどうか確認できるように例外的に）
> 境界線に一定間隔で濃い点が見える。半透明線の重なり？

1. **濃さを1.5倍にした。** 手前 0.18 → **0.27**、遠く 0.05 → **0.075**
2. **打った後のカメラでは出さないようにした。** 例外は `FOLLOW`（打った直後の
   最初のプレイヤー視点）だけ。`CUP`（カップ確認）と `RESULT` 以降（停止後の俯瞰）では消える。
   次の一打の `ADDRESS` でまた出る。
   実測で、停止後の俯瞰に出ていた境界の画素は **12959 → 0**
3. **一定間隔の濃い点は、半透明の線を2回に分けて描いていたのが原因だった。**
   濃さを距離で決めるために8段へ丸め、**段ごとに stroke していた**ので、
   段の変わり目で隣り合う線分の丸い端が重なり、そこだけ2回塗られていた。
   段の境目は距離で決まるので、**点が一定間隔に並ぶ**。
   → **線分をまとめて1回で stroke する**ようにした。1回なら重なっても濃さは変わらない。
   距離による薄まりは**画面の縦方向のグラデーション**に置き換えた
   （線は地面に乗っているので遠いほど画面の上に来る）。
   段に丸める必要がなくなったので、薄まり方もなめらかになった

## 7. 進行表示（何ホール目・何打目）が読み取りにくい（新規・2026-09-13）

**完了（実機確認OK・2026-09-15）。** 下の「残りの確認」はすべて問題なしだった。

### 症状

プレイ中に「今が何打目か」がすぐ分からない。何ホール目かも含めて把握しづらい。

### 現状の実装

HUDは1行だけで、すべて同じ大きさの等幅で並んでいる（`progressText()` / `src/i18n.ts`）。

```
HOLE 3/9  PAR 4  2打 +1  3.42m
```

- 5つの数字が同じ重みで並ぶため、視線が「今の打数」へ行かない
- 打数とパー差（`2打 +1`）が隣り合っていて、どちらが打数か一瞬迷う
- 折り返しを避けるため区切りは空白だけ。区切りとしても弱い
- カード表示中はHUDごと引っ込む（`quiet`）ので、ホール番号を確認する場所が無い瞬間がある

### 参考にした中継の整理

ゴルフ中継は同じ項目でも「常時／局面／節目」で出し方を変えている。

| 項目 | 中継での出し方 | いつ |
|---|---|---|

## 8. カップイン直後にカードが出てラインを確認できない（新規・2026-09-13）

### 症状

### 現状の実装

### 修正

- `cardDelay` を俯瞰への遷移が終わってから数え始めるようにした。
  カードが出るのは停止から `settleDelay` + `transition` + `cardDelay` = 約2.95秒後になる

- 値そのもの（0.8秒）と物理・罰打計算は変更していない

俯瞰へ着いてからラインを読む間があるか、逆に長すぎないかを実機で確認する。

### 残りの確認

- 軌跡を見る時間を何秒取るかは実機で決める（今は0.8秒）

## 9. ホールアウトのジングルが浮く（新規・2026-09-13）

**完了（実機確認OK・2026-09-15）。** 下の「新案」を本編へ入れた。

浮きは解消し、結果の違いも伝わり、カードの間の無音も気にならなかった。
環境音を足す検討は不要になった。数値（引き0.35秒・戻り0.7秒・音量0.22）はこのままとする。

### 症状

ホール間に鳴るジングルが、ゲームの音の中で浮いて聞こえる。もっと静かにしたい。

### 現状の実装

`src/music.ts` の `playHoleOutJingle()`。カップ音の余韻を聞かせるため約1秒遅らせて鳴らす。

浮いて聞こえる理由として、実装上そろっている条件:

- **BGMは同時和音を前へ出さない方針**（ベース + 単音PSG + ノイズ）なのに、
  ジングルだけ4声（C6/9）を2回**同時に**鳴らしている。テクスチャが1箇所だけ違う
- 音色が矩形波 + ノイズヒットで、BGMのトライアングル主体より硬い
- ジングル用のバスを**BGMバスを通さず `context.destination` へ直結**している（`JINGLE_GAIN` = 0.28）。
  シーンの音量調整の外にいる
- 鳴り出しがBGMの拍・小節に同期しておらず、進行中のコードとも無関係に常にC6/9で鳴る
- BGMを 0.78 までしか下げない（`JINGLE_DUCK_RATIO`）ので、別々の曲が重なって聞こえる

### 方向（どれか一つずつ試す。まとめて変えない）

- 音量を下げる（`JINGLE_GAIN`）
- 同時和音をやめ、BGMと同じ単音の動きにする
- 矩形波 + ノイズをやめ、トライアングル中心の柔らかい音にする
- 鳴らす位置をBGMの拍・現在のコードへ合わせる
- ジングルをやめて、カップ音の余韻 + BGMのわずかな持ち上げだけで済ませる案も候補にする

音の判断は実機（スピーカー・イヤホン両方）で行う。数値は `src/config.ts` へ寄せるかも含めて決める。

### 新案: BGMを止めて、カードと同時に結果別のジングル（2026-09-15）

試遊者の案。**浮いて聞こえる一番の理由（BGMとジングルという別々の曲が同時に鳴っている）を、
重なり自体をなくして消す。** 対症療法の下の5案より根が深いところを直している。

流れ:

1. カップ音は今のまま、ボールが落ちた瞬間に鳴る
2. 俯瞰へ移り、ラインを見る間を取る（§8で入れた待ち）
3. **スコアカードが出るのと同時**に、BGMを速めのフェード（0.35秒）で引き、結果別のジングルを鳴らす
4. カードを見ている間は無音
5. **次のホールの開始と同時**にBGMを戻す（0.7秒のフェードイン）

決めたこと:

- BGMは止めずに**音量だけ引き、曲は裏で進ませる**。毎ホール同じ出だしに戻らないようにする
- **ギブアップでは鳴らさない。** ホールは終わるがカップインはしていないので、追い打ちにしない
- カード表示中の無音が寂しいかは実機で見る。気になれば環境音を足すことを検討する

結果は5段階。`HoleOutResult` として持ち、`playHoleOutCue()` で鳴らす。

| 結果 | 形 | 中身 |
|---|---|---|
| イーグル以上 | 上行4音 | ソ→ド→ミ→ソ。ここだけ長め、高域に薄いきらめき |
| バーディ | 上行3音 | ソ→ド→ミ。最後をオクターブ上の単音で薄く重ねる |
| パー | 2音 | ソ→ド。主音で着地。5つで一番地味に |
| ボギー | 下行3音 | ラ→ソ→ミ。ベースもラへ動かす |
| ダボ以上 | 下行3音 | ソ→ミ♭→ド。♭で沈む。一番短く一番小さく |

5つとも**同じ2〜4音の形**で、上へ行くか下へ行くか、♭が入るかだけが違う。
別々の曲に聞こえないので、9ホール続けても結果の違いだけが伝わる。
音色はBGMと同じ（三角波のベース + 単音のPSG）。同時和音とノイズヒットは使わない。
BGMを止めてから鳴らすので、音量は従来の 0.28 より小さい 0.22 で足りる。

**この案を本編へ入れた（2026-09-15）。**

- `src/main.ts` の `showVerdict()` が、カードの結果を `#score-title` の `data-result` に書く
  （ギブアップは `none`）
- `src/audio-bootstrap.ts` の `installHoleOutMusic()` がそれを見て `playHoleOutCue()` を呼ぶ。
  カードが消えたら `resumeAfterHoleOut()` でBGMを戻す
- main.ts は音を直接呼ばない。既存のラウンド終了曲の切り替えと同じ繋ぎ方に揃えてある
- カップインの瞬間に鳴らしていた従来のジングル（`playHoleOutJingle`）は削除した

### 試聴ページ（2026-09-15）

聴き比べのために、上の5案（`JingleVariant` = `quiet` / `single` / `soft` / `inTime` / `none`）と
現状を `/jingle-test/` で鳴らし分けられるようにしていた。**実機で新案の採用が決まったので、
比較用の6案と `playHoleOutJingle` / `ACTIVE_JINGLE` は削除した。**

- 試聴ページ `/jingle-test/` は残す。結果別の5つを、本編と同じ流れ

## 11. 木のバリエーションと細部の作り込み（新規・2026-09-16）

**完了・実機確認OK（2026-09-20）。** §12（コースごとの雰囲気）と一緒に入れた。

### 分かっていること

- **コース生成器とは無関係。** `createTrees()` は**出来上がったサーフェスマップを読んで**
  OBエリアに置いているだけ。触るのは `src/green.ts` の `createTrees` /

- OBエリアに置くこと自体が「どこからOBか」の手掛かりになっている（`TASKS.md` の経緯）ので、
  **5-1（OB境界の視認性）と一緒に見ると判断しやすい**

### やらないこと

- 立体の障害物として当たり判定を持たせること。反射を物理へ足すことになり、
  決定論とリプレイの前提が重くなる（`docs/course-generator-v2.md` §2-3 で不採用と決めた）

### 直した内容（2026-09-20・実機確認待ち）

**円柱1本＋円錐1個をやめ、樹種を3つにした。** 数値は `CONFIG.trees`、組み立ては
`src/green.ts` の `createTrees`。**どの樹種でも幹は鉛直のまま**で、輪郭の崩しは枝と葉でやる。

| 樹種 | 作り方 | 使うところ |
|---|---|---|
| 広葉樹 | 丸い塊（正二十面体）を3〜5個ずらして重ね、枝を2〜3本出す | BEGINNER・STANDARD |
| 針葉樹 | 円錐を3〜4段、段ごとに半径と向きを変えて積む | STANDARD・ADVANCED |
| 低木 | 組み方は広葉樹と同じで、背が低く横に広い | EXPERT |

**1本ごとに乱数で揺らぐ**（`CONFIG.trees.jitter`）。葉と幹の色・幹の太さ・葉の広がりと高さ・
塊や段の数と半径・枝の本数と向き・取り付け位置。

- **色は1本につき1回だけ引く。** 部位ごとに振ると1本の木が縞に見える
- 色の揺らぎは**ドット化の量子化より大きく振る**（`pixel.colorLevels` 48 ＝ 1チャンネル
  約5.3/255）。±14% なら ±15/255 になり、段に潰れない
- **針葉樹は段数が違っても木の高さを揃える。** そのまま積むと4段の木が3段より2割高くなり、
  テーマの `heightMin` / `heightMax` が意味を持たなくなる
- **塊の半径は 0.20 では小さすぎた**（低い木が「棒の先に飴玉」に戻る）。0.26 にした

**部品は1つのジオメトリへまとめ、色は頂点カラーへ焼く。** 1本ごとに色が違っても
描画は1回で済み、**1ホールぶんの木がメッシュ1個**になった（木14本で28個だった）。

### 1回目の実機で出た指摘と直し（2026-09-20）

> 幹と葉っぱの部分がすきまできているところがある
> standardとadvancedは木が全体に大きすぎる
> standardは2種類の樹の混ざり方がわざとらしいというか、不自然な感じ

1. **幹と葉の隙間。** 原因は**正二十面体の面が半径の 0.79 倍のところにある**こと。
   半径ぶん持ち上げて置いていたので、見た目の底面が幹の上端より上に来ていた

   **2個目以降の持ち上げにも潰しを掛ける**ようにした。どの揺らぎの組み合わせでも、

2. **木が大きすぎる。** STANDARD 3.5〜6.5m → **2.8〜4.8m**、
   ADVANCED 5.0〜8.5m → **3.6〜6.0m**（それでも4コースで一番高い）
3. **混ざり方がわざとらしい。** 樹種を1本ずつ乱数で引いていたので、広葉樹と針葉樹が
   交互に並んでいた。→ **位置のなめらかなノイズで決める**ようにした。
   実際の林と同じで**近くの木どうしは同じ樹種**になり、林がまとまって見える。

## 13. 高難度コースの解放（新規・2026-09-17）

> コースで速さ変えるのは難易度高いとこでやるのはいいんですが（略）

- B. どれか1コースをパー以内で回ったら解放（腕前で解放。初心者に開かない危険）

- D. 解放しない。最初から見えているが「上級」と明示（いちばん安い）

**Aを推す。** 保存は自己ベストと同じ `localStorage`。

- 解放コースを**オンラインランキングの対象にするか**（速さが違えばスコアの意味が変わるので、
  分けるのが自然）

## 14. カップぎわのけられと、旗竿の反発（新規・2026-09-18）

**実装済み・実機確認待ち。**

### 症状（試遊で出た2件）

- カップぎわで球がけられる動きが弱い。**もう少し大げさにしたい**
- **旗竿の反発係数が大きすぎる。** 跳ね返りが大きく、カップインせずに跳ね返りやすい

### 分かったこと: 2件は同じ判定の表裏だった

`src/physics.ts` の `checkCup()` は、口（半径54mm）へ入った球を**横ずれ**で振り分けている。

- 横ずれ **0〜33.3mm** → 旗竿に当たる（`flagstickRadius` 12mm + ボール 21.3mm）
- 横ずれ **33.3〜54mm** → 竿に触れず口をなめる ＝ リップアウト

つまり口に入った球の横ずれの6割は竿の判定へ行くので、
**「カップぎわのけられ」の見た目の大半は旗竿の跳ね返りが作っている。**
片方だけ動かすともう片方を打ち消すため、2件を1つの調整として扱った。

もう一つ、**「跳ね返りを弱くする」と「入りやすくする」も同じ数値で結合している。**
カップインの判定が**衝突後**の速度（`flagstickCaptureSpeed` 未満なら落ちる）なので、
`flagstickRestitution` を下げると衝突後の速度が下がり、入る入射速度の上限が勝手に上がる。
0.25 → 0.12 にしただけだと芯の上限が 2.40 → 5.00 m/s になり、
**最強の一打の初速が約4.0m/s** なので「芯を突けば必ず入る」になってしまう。
`flagstickCaptureSpeed` を一緒に下げて、上限を狙った位置へ置き直している。

### けられの角度に速度を入れた（2026-09-18・試遊での指摘）

**「蹴られる角度は、実際は球の速さとカップへの進入位置に影響されるはず」**との指摘。
調べたら**進入位置は入っていたが、速度は入っていなかった。**

`grazeCup()` の曲がりも減速も `grazeChord`（進入位置から出る弦の長さの比）だけで決まっていたため、
**入る寸前でぎりぎり落ちなかった球も、4m/s で撃ち抜いた球も、同じ横ずれなら同じ 25.6° 曲がっていた。**
口を横切る時間は `弦 / 速度` なので、速い球ほど落ち込む間がなく曲がらないのが正しい。

**新しい設定値は足していない。** この分岐へ来る条件がそもそも
「速度 ≥ 捕まえられる上限」なので、`上限 / 速度` が必ず 0〜1 に収まる。
これを弦に掛けた `effect` で曲がりと減速を出す（落ちる寸前で 1、速いほど 0 へ）。

| 横ずれ | 速度 | 前の曲がり | 後 | 前の減速 | 後 |
|---:|---:|---:|---:|---:|---:|
| 34mm | 1.11（入る寸前） | 26.7° | **26.2°** | 31% | 30% |
| 34mm | 2.00 | 26.7° | **14.5°** | 31% | 17% |
| 34mm | 4.00 | 26.7° | **7.3°** | 31% | 8% |
| 50mm | 0.54（入る寸前） | 13.0° | **12.7°** | 15% | 15% |
| 50mm | 4.00 | 13.0° | **1.7°** | 15% | 2% |

**この時点では最大の曲がり 27.1° を変えていない**（この後 60° へ上げた。下の節）。
「あと少しで入った球が大きく弾かれる」という見せたい瞬間だけが残り、
速い球が不自然に曲がるのが消える。
`cupGrazeTurn` の意味は**「入る寸前の球での曲がり」**になったので、
足りなければ従来どおりこの1つを上げれば効く。

触ったのは `src/physics.ts` の `grazeCup()` と口へ入る瞬間の数行だけ。
`check:stuck` は v1・v2 とも詰み0・カップイン可で、決定論の確認も通っている。

### 最大の蹴られ角度を60°へ上げた（2026-09-18・プレビュー確認）

**「勢いが弱かったら60度くらいは現実でもたまにある」**との指摘を受け、
`cupGrazeTurn` を 0.6 → **1.33** にした（最大ちょうど 60.0°）。
速度依存が入った後なので、**60°が出るのは落ちる寸前の遅い球だけ**で、
速い球はほとんど曲がらない。

| 横ずれ | 速度 | 曲がり | 減速 |
|---:|---:|---:|---:|
| 34mm | 1.11（入る寸前） | **58.0°** | 30% |
| 34mm | 2.00 | 32.2° | 17% |
| 34mm | 4.00 | 16.1° | 8% |
| 50mm | 0.54（入る寸前） | 28.2° | 15% |
| 50mm | 4.00 | 3.8° | 2% |

健全性を確認した。`cupGrazeTurn` を 0.6 / 1.0 / 1.33 / 1.6 と振っても、
**止まらなかったショットは0**で、なめる帯のカップイン数も103で変わらない
（＝曲げた球が口へ戻って周回するようなことは起きていない）。
曲がりは口から**出るとき**に一度だけ与えるので、竿の当たり判定へ回り込む心配もない。

### 「横にずれて旗竿に当たると入りづらくなった」の裏取り（2026-09-18）

プレビューでの指摘。**横ずれ0〜52mm × カップ到達速度0.3〜3.0m/s の1512通りを
本物の物理で転がして旧値と1対1で突き合わせたところ、
「旧は入ったのに新は入らない」は0件だった**（新たに入るようになったのが70件）。
カップインしやすさ自体はどこも悪化していない。

**ただし、そう感じる理由は本物。**

| 横ずれ | 旧 | 新 |
|---:|---:|---:|
| 0mm | 76.4% | **100.0%** |
| 6mm | 65.5% | **87.3%** |
| 12mm | 49.1% | 52.7% |
| **18mm 以上** | 38.2% | **38.2%（不変）** |
| 30mm | 30.9% | 30.9% |

**芯だけが跳ね上がって横ずれは完全に据え置き**なので、芯と横ずれの差が広がった。
前は 芯76% : 20mm 36%（比0.48）、今は 芯100% : 20mm 36%（比0.36）。
さらに `flagstickRestitution` を下げたぶん**弾かれた球が大きく跳ねずにその場で止まる**ので、
「弾かれた」ではなく「ただ入らなかった」に見える。

**18mm以上が動かないのは、そこでは旗竿の上限より
カップの口の弦で決まる上限（`cupCaptureSpeed` 1.4）のほうが低いから。**
旗竿の3値をいくら触っても18mm以上は1mmも変わらない。
**横ずれ時も入りやすくしたいなら、動かすのは `cupCaptureSpeed`。**
旗竿とは独立に効くので、実機で必要と判断したら単独で上げられる。

### 旗竿の判定を「当たったときの速さ」だけで決める形にした（2026-09-18・プレビュー確認）

プレビューで出た3件。**どれも同じ設計の問題だったので、1つの変更でまとめて直した。**

1. 横ずれ0mmで100%入るのはやめたい
2. 強すぎたら手前に跳ね返るようにしたい
3. 同じ強さで旗竿に当たるとき、入る確率は横ずれ量によってあまり変えない方がリアル

**原因は「入るかどうかを衝突“後”の速度で見ていた」こと。**
反射は法線と接線で分けるので、横ずれが変われば衝突後の速度も変わる。
結果、入る確率が横ずれに強く引きずられ（芯 3.75m/s まで入る一方、竿の縁は 0.70m/s まで）、
芯では何を打っても入ってしまい、しかも `flagstickRestitution` を下げないと
その上限が跳ね上がるので跳ね返りも作れない、という三すくみになっていた。

**判定を衝突“前”の速さに変えた。** 竿は芯で受けても縁で受けても球を止める向きに働くので、
「弱ければ落ちる・強すぎれば入らない」は横ずれによらず同じように起きる、と考えるほうが素直。
`flagstickCaptureSpeed` の意味が**「当たった瞬間の速さの上限」**になり、
`flagstickRestitution` から独立した。

| | 前 | 後 | 何が変わるか |
|---|---:|---:|---|
| `flagstickCaptureSpeed` | 0.45（衝突後） | **2.1（衝突前）** | 竿に当たって入る上限。**横ずれによらず一定** |
| `flagstickRestitution` | 0.12 | **0.3** | 入らなかった強い球が手前へ戻る |

2.1 m/s はカップを 4.0m 過ぎる強さ。
1.6 →（きびしい）→ 3.2 →（入りやすすぎる）→ 2.3 →（まだ少し入りやすい）→ **2.1 で確定**。
`flagstickRestitution` を戻せるのは、**弱い球はもう弾かれずに落ちるから**。
ここが効くのは「強すぎて入らなかった球」だけになり、前の「普通の球まで跳ね返る」は起きない。

実測（平らなグリーン・カップへ真っ直ぐ・到達速度 0.3〜3.0m/s を0.05刻み）。

| 横ずれ | 竿に当たって入る上限 |
|---:|---:|
| 0mm | 2.05 m/s |
| 12mm | 2.05 m/s |
| 20mm | 2.05 m/s |
| 32mm | 2.05 m/s |
| 36mm（竿の外） | 1.00 m/s（口の弦で決まる） |

**0〜32mm が完全にフラット**になった（前は芯 3.75m/s → 竿の縁 0.70m/s）。
弾かれた球の向きも横ずれで分かれる。**芯寄り（〜18mm）は手前へ戻り、
20mm より外は接線成分が勝って先へ流れる**（32mm で 1.7m 先）。
33.3mm から先は竿に触れない帯なので、口の弦で決まる上限へ自然に落ちる。

手前への跳ね返り（横ずれ0mm・+ がカップの手前）。

| 到達速度 | 結末 | 止まった位置 |
|---:|---|---:|
| 2.00 m/s | カップイン | – |
| 2.20 m/s | 弾かれ | +0.43 m |
| 2.60 m/s | 弾かれ | +0.59 m |
| 3.00 m/s | 弾かれ | +0.77 m |
| 4.00 m/s | 弾かれ | +1.34 m |

`check:stuck` は v1・v2 とも詰み0・カップイン可・決定論OK。

**実機で見てほしいところ**

1. ~~線引きが妥当か~~ **2.1 m/s（カップを4.0m過ぎる強さ）で確定。**
   **強すぎて入らない**のが理不尽に感じないか
2. 手前への跳ね返りの量。`flagstickRestitution` 0.3 で強い球は1m以上戻る
3. 横ずれによらず一定になったことで、**竿に当たりさえすれば良い**と感じないか。
   感じるなら `flagstickCaptureSpeed` を下げる（竿に当たっても入りにくくなる）
4. 竿に当たる帯（0〜33.3mm）と、なめる帯（33.3mm〜）の境目が不自然に見えないか

### まとめ: 最終的な値（`src/config.ts` の5つ。判定の形は `physics.ts`）

| | 元 | 最終 | 何が変わるか |
|---|---:|---:|---|
| `cupGrazeTurn` | 0.3 | **1.33** | なめたときの曲がり 最大 12.8° → **60.0°**（遅い球のみ） |
| `cupGrazeSpeedLoss` | 0.25 | **0.4** | なめたときの減速 最大 19% → **31%**（遅い球のみ） |
| `flagstickCaptureSpeed` | 0.6（衝突後） | **2.1（衝突前）** | 竿に当たって入る上限。**横ずれによらず一定** |
| `flagstickRestitution` | 0.25 | **0.3** | 入らなかった強い球が手前へ戻る |
| `flagstickTangentKeep` | 0.8 | **0.65** | 掠めたときに横へ流れる量を落とす |

`physics.ts` 側は2つ。**なめる効きに速度を入れた**のと、
**竿の判定を衝突前の速さに変えた**。どちらも設定値は増やしていない。

**途中経過として、旗竿は一度 `flagstickRestitution` 0.12 /
`flagstickCaptureSpeed` 0.45（衝突後）を通っている。**
その版は芯で 3.75m/s まで入り、横ずれ18mm以上は据え置きという偏った形だった
（上の「入りづらくなった」の裏取りはその版の数字）。
プレビューの指摘を受けて判定の形ごと変えたので、**その中間の数字はもう当てはまらない。**

`npm run check:stuck --seeds=1-20` を v1・v2 の両方で通した。
詰み0・カップから1m以内で入れられなかったマス0（v1 250マス / v2 252マス）・決定論OK。

### 実機で見てほしいところ

1. **けられが「大げさ」として気持ちよい量か。** 足りなければ `cupGrazeTurn` を上げる
   （実際に出るのは値の8割までで、しかも**入る寸前の球でのみ**。速い球は曲がらない）
1-2. **速い球のけられが小さくなったのが自然か。**
   「強い球ほど弾かれてほしい」と感じるなら速度依存の向きが逆なので、その場で言ってほしい
2. ~~竿に当たって入る線引き~~ **到達 2.1 m/s で確定**（プレビューで 1.6 / 3.2 / 2.3 / 2.1 を試した）。
   11m 手前までならこの速さで到達できるので、**ほとんどの距離で弾かれうる**
   効くのは `flagstickCaptureSpeed` 単独（`flagstickRestitution` からは独立した）
3. **強すぎた球が手前へ戻る量。** 効くのは `flagstickRestitution` 単独
4. **横ずれによらず一定になったことで「竿に当たりさえすれば良い」と感じないか**
5. 竿に当たる帯（0〜33.3mm）と、なめる帯（33.3mm〜）の境目が不自然に見えないか
