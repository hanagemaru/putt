# パッティングゲーム 試作仕様

スマホ縦画面・ブラウザで動く一人称パッティングゲームのプロトタイプを作ってください。
**グラフィックは最小限（単色・簡易形状）で構いません。** 目的は物理挙動と操作感、カメラ遷移の検証です。見た目は後から差し替えます。

---

## 0. 技術スタック

- Vite + TypeScript + three.js
- 物理エンジンは使わない（自前の単純な転がり計算）
- パラメータ調整用に `lil-gui` を入れる
- `npm run dev` で起動、スマホ実機確認用に `--host` を有効化
- **縦画面専用。** 横画面のときは「縦にしてください」のオーバーレイを出す

横画面にするのは遊ぶ側の一手間になるので、縦のまま遊べることを優先する。

ディレクトリ構成の目安:

```
src/
  main.ts          エントリ、状態機械
  config.ts        全チューニング定数（ここ以外に数値を散らさない）
  green.ts         ハイトマップ生成・サンプリング・メッシュ構築
  physics.ts       ボールの転がり計算
  input.ts         スワイプ検出とストローク解析
  cameras.ts       各カメラの定義と補間
  debug.ts         lil-gui とデバッグ表示
```

## 1. グリーン

### データ

- サイズ 20m × 20m、XZ平面、Y が高さ（three.js 標準の Y-up）
- 内部は 256×256 の `Float32Array` ハイトマップ
- 生成は手続き的に。ガウシアン数個＋緩やかな全体傾斜を合成する。シード指定で再現可能にすること
- 起伏の大きさは実際のグリーン相当（全体傾斜 1〜3%、うねりの振幅 ±0.15m 程度）
- 任意座標の高さと勾配はバイリニア補間で取得する `sampleHeight(x, z)` / `sampleGradient(x, z)` を用意

### 描画

- `PlaneGeometry(20, 20, 128, 128)` の頂点を高さで変位
- **頂点カラーで濃淡をつける。濃淡が表すのは「高さ」ではなく「斜面の向きと強さ」。**
  固定方位の光ベクトルと勾配 ∇h の内積で明暗を決める。これがアンジュレーション表現の主軸
  - **絶対スケール。** フルレンジを勾配 `shadeGradientRange`（初期値 8% ＝ 臨界勾配相当）に取り、
    「同じ明暗差 ＝ 同じ勾配 %」を全シードで保つ。グリーンごとの最小最大で正規化しない
  - 高さベースの濃淡も弱く重ねる（地形のマクロな高低が消えないように）
  - 高さを主軸にしていた頃は、一人称の視野（半径数メートル）の高低差が数センチしかなく、
    明度差が 3% にしかならなかった。俯瞰でしか読めない表示だったので勾配ベースへ変えた
- 加えて `computeVertexNormals()` と低い角度の `DirectionalLight` を入れる。陰影で「形」が出るかを見たいので、色の濃淡と光の陰影の寄与比を lil-gui で調整できるようにすること
- マテリアルは `MeshLambertMaterial({ vertexColors: true })` 程度で十分

### ホール

- 直径 108mm、深さ 100mm の円筒（見た目は暗い円で可）
- 旗竿は**必ず鉛直**に立てる（傾き表現の基準として重要）
- 背景に木を模した簡易オブジェクトを数本、グリーン外周に配置（これも傾きの基準になる）

## 2. 物理

固定タイムステップ 1/240 秒で更新。決定論的にすること（後でリプレイに使う）。

```
勾配による加速度: a_slope = -(5/7) * g * ∇h        // 転がる球なので 5/7
摩擦による減速:   a_fric  = -MU * normalize(v)      // 速度に依らず一定
```

- `MU` はスティンプ換算で決める。スティンプ 10ft の場合、初速 1.83 m/s で 3.05m 転がるので `MU ≈ 0.55 m/s²`。config でスティンプ値を指定して逆算する形にする
- 速度が 0.02 m/s を下回ったら停止。ただし勾配が摩擦を上回る場所では停止させず転がり続けさせる
- グリーン外に出たら停止して「グリーンオーバー」扱い

### カップ判定

- ボール中心がカップ中心から 54mm 以内に入ったとき
- 速度が `CUP_CAPTURE_SPEED`（初期値 1.4 m/s）未満ならカップイン
- それ以上なら**リップアウト**：カップの縁で速度ベクトルを反射させ、少し減速させて転がり続ける

## 3. 状態機械

```
READ → ADDRESS → STROKE → FOLLOW → CUP → RESULT → (次のパット or READ)
```

### READ（読み）

4つの定点カメラを左右スワイプで切り替える。それぞれ視点高さは現実的に。

1. `BEHIND_BALL` — ボール後方 1.5m、高さ 1.6m、カップ方向を向く（デフォルト）
2. `BEHIND_HOLE` — カップ後方 1.5m、高さ 1.6m、ボール方向を向く
3. `LOW_LINE` — ボール後方 1m、高さ 0.4m（しゃがみ）
4. `SIDE_MID` — ボールとカップの中間点の横 2m、高さ 1.6m、ラインを横から見る

タップで ADDRESS へ。

### ADDRESS（構える）

- 視点高さ 1.5m、ボールを見下ろす角度、カップ方向を向く
- **カメラに ROLL（傾き）をかける。初期値 12度。** これはアドレス姿勢で顔を傾けたままピンを見ている状態の表現
- 左右スワイプで狙い方向（ヨー）を変更。**補助線は一切出さない**
- タップで STROKE へ。**このとき ROLL は 0 に戻る**（ボールを見る姿勢では視野は傾かない）
- ADDRESS ⇄ STROKE のカメラ遷移は 0.25秒以内、またはカット。ロール回転を長く見せないこと

### STROKE（打つ）

- 真下を見下ろす視点。画面上方向＝狙った方向
- 見えるのは**ボール、パターヘッド、つま先のみ**（それぞれ単色のボックス／球で可）
- ホール、旗竿、背景は一切見えない
- パターヘッドは指の動きに追従して**左右にも上下にも動き、フェースがスイング軌跡と直角に傾く**（§4.4）
- スワイプ入力を待つ（§4）

### FOLLOW（顔を上げて追う）

- カメラ位置はプレイヤーの目のまま固定。**ヨーとピッチだけでボールを追う**
- **打った直後は視点を動かさない。** ボールが STROKE の視界から出るまでは真下を見下ろしたまま。
  すぐに顔や目線を動かさないのが安定したストロークの所作なので、そこに合わせる
- ボールが視界から出てから 0.15秒かけて視点が上がる。**このとき初めてホールが視界に入る**
- ボールが遠ざかるにつれて FOV を 70° → 35° へ絞る（目を凝らす表現）
- **カメラは平行移動しない。** ボールについて行ってしまうと曲がりが見えなくなる

### CUP（決着）

- ボールがカップまで 1.5m を切ったら、カップ後方・芝の高さ（Y=0.05m）の定点へカット
- ここで最後の曲がりと速度が見える

### RESULT（答え合わせ）

- **ボールが完全に停止してから**、斜め45度の俯瞰へ遷移
- ボールの軌跡を線で表示（走行中は表示しない、止まってから出す）
- 結果テキスト: `カップイン` / `2.3m ショート` / `0.8m オーバー、左 0.4m`
- タップで次のパットへ（停止位置から継続）

**重要: 走行中に俯瞰へ抜かないこと。** 一人称のまま最後まで見せて、分析は止まってから。

## 4. ストローク（スワイプ入力）

これが本体です。丁寧に作ってください。

### 4.1 画面と向き

**縦画面前提。** 横幅が狭い（iPhone で約 390px）ので、バックスイングと振り抜きに使える距離が横画面より短い。所作の幅と必要な速度域が両立するかは実機で確認する（§8）。

ボールは画面中央。画面上方向＝狙った方向。

### 4.2 検出

1. 画面のどこでもよいので指を置く（`pointerdown`）
2. **右へドラッグ**＝バックスイング（右打ち想定。config で左右反転可能に）
3. 方向が反転して**左へ動き**、**フェースがボールの右端に触れた瞬間**がインパクト。
   判定ラインはボールの X ＋ ボール半径 ＋ フェース厚みの半分。ボール中心で判定すると、
   当たる前にパターがボールへめり込んで見える
4. 指は最後まで画面につけたまま。`pointerup` は判定に使わない

**バックスイングなしにいきなり左へ動かした場合は無効（打たない）。** これを正しく効かせるには、幅の測り方が要点になる。

- バックスイング幅は **「指を置いた点から右へ実際に動かした量」** で測る。ボール中心からの距離で測ってはいけない。後者だとボールより右に指を置いただけで幅が計上され、右に引かずに左へ払うだけで打ててしまう
- 幅が `minBackswingPx`（初期値 40px）を超えるまでダウンスイングを解禁しない（＝アームしない）。未アームの間は判定ラインを左へ横切っても打たない
- 未アームで横切ってもストロークは終了させない。**そのまま引き直して振れば成立する**
- 未アームのまま横切って指を離したときだけ「バックスイングなし」として通知する。ただのタップでは通知しない
- 画面上に**バックスイングのゲート線**（指を置いた点 + `minBackswingPx`）を出し、打てる／打てない状態を色で示す

### 4.3 速度の算出

- `pointermove` を全てタイムスタンプ付きでリングバッファに保存（`event.getCoalescedEvents()` を使って取りこぼしを防ぐ）
- インパクト時刻の直前 40ms のサンプルに**最小二乗フィット**をかけて速度を出す。単純な2点差分はノイズが多すぎるので使わない
- 窓内のサンプルが足りない端末（60Hz など）では、必要数に届くまで窓を広げる
- 交差点は線形補間してインパクト時刻を求める。サンプリング周期で結果がぶれないようにする
- 端末のリフレッシュレート差（60/120Hz）が結果に出ないことを確認する

### 4.4 パターヘッド

真上から見たフェースを縦長の矩形で表す。

- 長さ `putterLength`（初期値 64px）
- X = 指の X
- **Y = ボールの Y ＋（指の Y − 指を置いたときの Y）**
- 向きは**スイング軌跡と直角**。インパクト直前の速度ベクトル `(vx, vy)` の垂線

指を置いた位置が基準なので、画面のどこで構えても同じ所作になる。

パターヘッドは**指を置く前から見えている**。待機位置はボールの右 `putterRestOffsetPx`（初期値 36px）で、
フェースは狙い方向と直角（画面上では垂直）。

**フェースは反転させない。** 軌跡の垂線をそのまま使うと、右へ引いている間は面の法線が右を向き、
ループ軌道になると打つ瞬間に面が入れ替わる。真上・真下へ動いた瞬間には面が横倒しになる。
狙い方向を基準に、右向きの動きは鏡映して扱い、傾きは `faceMaxAngle`（初期値 35度）で頭打ちにする。

**インパクト後もパターは指に追従する。** 指から切り離して惰性で流すと、打ったあとにパターだけが
左へ滑っていくように見えて不自然だった。指を離したらアドレス位置へ戻る。

**ただしパターがボールを追い越さないこと。** インパクト後は、フェースの X をボールの右端
（ボールの X ＋ ボール半径 ＋ フェース厚みの半分）で頭打ちにする。ボールは指より速く離れていくので、
普段はすぐ効かなくなる。

### 4.5 芯とミスヒット

インパクト時の接触位置のズレを次で定義する。

```
offset = ボールのY − パター中心のY        // ＝ 指のY変位の符号反転
```

- `|offset| <= sweetSpotPx`（初期値 12px）→ 減衰なし
- そこからフェース端までで線形に `mishitMinGain`（初期値 0.55）まで落とす
- `|offset| > putterLength / 2` → **空振り**。打たない

**勢いだけを落とし、方向は変えない。** 実物のパターはヒール／トウ側で打つとフェースが開いてボールが曲がる（ギア効果）が、まずは減衰だけにする。効いているパラメータが実機で分からなくなるのを避けるため。必要なら後から足す。

### 4.6 フェース角と打ち出し方向

```
ボール初速 [m/s] = swipeVelocityX [px/s] * SPEED_K * ミスヒット減衰
```

- `SPEED_K` の初期値は 0.00133（1500 px/s のスワイプで約 2.0 m/s）。lil-gui で調整
- **打ち出し方向**: インパクト時のスワイプ角度 `atan2(vy, vx)` を狙い方向からのオフセットとして加える。ただし `DIRECTION_SENSITIVITY = 0.4` を掛けて鈍らせる（方向はシビアすぎないようにする）

4.4 でフェースをスイング軌跡と直角に描くのは、**この既存ルールを目に見えるようにするもの**であって新しいルールではない。フェース角＝インパクト時の速度ベクトルの向きなので、両者は同じ量を指している。

- バックスイングの幅は結果に影響させない（所作としてのみ扱う）

### 4.7 ボールの反応（検証ページのみ）

インパクトしたら、ボールが計測速度（ミスヒット減衰込み）に応じて左へ動き出し、減速して停止する。**ちゃんと打てたことが分かるためのフィードバック。**

速度はスワイプの px/s ではなく、**§4.6 で換算したボール初速 [m/s] を基準にする。** 画面のピクセルへは
`ballPxPerMeter` で直し、減速は `ballDecelMs2`（摩擦）を同じスケールで px/s² にする。
`ballDecelMs2` は演出用に実際のグリーンより小さくしてある（スティンプ換算で約 20ft 相当）。

転がる距離は `速度² / (2 × ballDecelMs2 × ballPxPerMeter)` なので、**この2つを同じ割合で動かすと
距離は変わらず、速さと減速だけが変わる。** 基準は「0.3 m/s で画面外まで転がる」に置く。

**この画面はボールに寄った近接視点なので、実際のパット程度の初速でもボールはすぐ画面外へ抜ける。それでよい。**
ごく弱いタッチ（0.3 m/s 程度）でも画面外まで転がるくらいが、ストロークの速さに対する手応えとして正しい。

**これは見た目だけの演出で、§2 の物理とは別物。** `/swipe-test/` 限定であって、ゲーム本体には持ち込まない。ゲーム側のボールの挙動は §2 のハイトマップと転がり計算が唯一の情報源であり、二重に持たないこと。

### 4.8 指がボールを隠す問題

真下視点だと指がボールに重なります。以下を実装して比較できるようにしてください。

- (a) ボールを大きめに描画する
- (b) ボールの周囲にリング状のハイライトを出す
- (c) タッチ位置をボールより 80px 手前にオフセットする（画面下寄りで操作、ボールは上に見える）

lil-gui で切り替えられるように。なお (c) を使う場合も、パターの上下位置と芯の判定は「指を置いた点からの Y 変位」を基準にするので、そのまま成立する。

## 5. デバッグ表示

常時オーバーレイで表示:

- 狙い方向（度）
- スワイプ速度（px/s）と換算後のボール初速（m/s）
- カップまでの距離（m）
- 直前の結果（オーバー／ショート量、左右のズレ）
- 現在の状態（READ/ADDRESS/...）
- インパクト時の芯からのズレ量（px）とミスヒット減衰の係数

lil-gui で調整可能にする項目:

- スティンプ値
- `SPEED_K`、`DIRECTION_SENSITIVITY`
- `minBackswingPx`（バックスイングのゲート）
- `putterLength`、`sweetSpotPx`、`mishitMinGain`（パターと芯）
- `faceMaxAngle`、`putterRestOffsetPx`（フェース角の上限と待機位置）
- `ballPxPerMeter`、`ballDecelMs2`（検証ページのボールの転がり）
- ADDRESS の ROLL 角度
- 濃淡の強さ（勾配）／濃淡のレンジ [勾配%]／高さの濃淡の強さ／ライト強度の比率
- ハイトマップのシード、うねりの振幅
- カップ捕捉速度
- 指の隠れ対策 (a)(b)(c) の切り替え
- **俯瞰カメラの自由化トグル**（開発用。読みフェーズでも俯瞰を出せるようにする。本番では無効）

---

## 6. モード

プロトタイプでは2つ。

- **ストローク**: カップインまでの打数
- **タイムアタック**: 打数不問、カップインまでの経過時間

READ フェーズの持ち時間制限を config で設定可能に（初期値は無制限）。

---

## 7. 実装しないこと

- 補助線、ライン予測、狙いのガイド表示
- STROKE 中のホール表示
- 走行中の俯瞰カメラ
- 凝ったテクスチャ、シェーダー、モデル
- サウンド
- コースデータの外部読み込み（今はコード内で生成）

## 8. 最初に確認したいこと

実装後、この順で検証します。

1. スワイプ速度から距離が**再現性をもって**出せるか（同じスワイプで同じ距離）
2. **縦画面の狭い横幅（約390px）で、必要な速度域とバックスイングの所作が両立するか。** 強く打つときに画面外まで指を振り切ってしまわないか
3. 芯を外す感覚が「自分のミス」として納得できるか。理不尽に感じないか
4. FOLLOW カメラだけで曲がりと強さが読み取れるか、CUP や RESULT がどれだけ必要か
5. 頂点カラーの濃淡だけで起伏が読めるか、ライトの陰影がどれだけ寄与するか
6. ADDRESS の傾きが「地面の傾き」と混同されないか

まずは動くものを最短で。凝った作り込みは不要です。
